## 2. Реалната цена при този стек

`FISHTAXI/index.html` = **154 KB ≈ 45 000 токена**.

Едно пълно пренаписване на файла от Fable:

```
45 000 × $50 / 1 000 000 = $2.25
```

40 итерации при дебъг сесия = **~$90 само от изхода**.
Точно така изгоряха първите $100 кредит.

**Изводът:** скъпото не е моделът, а **връщането на цял монолитен файл при всяка поправка.**
Изходните токени са 5x по-скъпи от входните.

## 3. Маршрутизация

### Ниво 0 — без модел (диагностика)

Преди да отвориш чат изобщо:

- счупен скрейп → `curl` към източника + diff срещу вчерашния HTML
- червен билд → лог от GitHub Actions
- JS не тръгва → `node --check`
- worker не отговаря → `curl` към endpoint-а

Класическите виновници тук са познати: промяна на селектор, cp1251 charset,
`dd.mm` парсване, изтекъл токен, кеш на raw CDN (~5 мин).

### Ниво 1 — GitHub-first (чети/пачвай/качвай през GH MCP, без артефакти)

Когато задачата пипа файл в репо, чети го през `GH:get_file`, направи патч,
качи го през `GH:put_file`. Никога не минавай през артефакт за неща, които
живеят на GitHub — това само добавя ненужни токени.

**Кой модел вътре в това ниво** — тук е грешката, която поправих:
„евтино защото няма артефакт" ≠ „евтино защото стига слаб модел".
Писането на коректен патч изисква разбиране на кода — това е Sonnet работа,
не Haiku, дори когато минава през GitHub MCP.

### Haiku 4.5 — само задачи без логика на код
Чист превод на съществуващ текст (BGR 14 езика), преформатиране на
JSON/CSV, regex когато шаблонът вече е зададен явно, commit съобщения.

### Sonnet 5 — работният кон, включително GitHub-first патчовете
Диагностика и поправка на счупен скрейпър, промяна на селектор/парсър,
CSS/UI корекция, нов скрейпър по познат шаблон, Actions YAML,
Kotlin boilerplate, тестове. **По подразбиране за read-patch-upload workflow.**

### Opus 5 — тук отива 90% от бившата Fable работа
Дебъг, изискващ разсъждение върху няколко файла едновременно, многофайлов
рефактор, архитектурно ревю, worker логика, `window.__applyLive` мостове,
KV/токен схеми.

> Fable е 2x над Opus по API цена, но за Pro съотношението е безкрайно:
> **Opus е безплатен, Fable не е.**

### Fable 5 — само проектиране, никога поправяне
Единственият валиден случай: **нова архитектура от нула**, където грешен
избор струва дни. Пример: първоначалният дизайн на такси приложението.

Забранено за Fable: дебъг, преводи, boilerplate, изследване „защо не работи",
пренаписване на файлове.

## 4. Протокол за Fable сесия

1. Подготви брифа в **Opus** (безплатно) — контекст, ограничения, желан изход.
2. Отвори **нов, кратък чат**. Не продължавай стар — дългият контекст се
   препрочита на всеки ход.
3. Поискай изрично: **патч или само променената функция, не цял файл.**
4. Вземи резултата и **затвори сесията.** Итерациите правѝ в Opus/Sonnet.

---

## 5. Структурни мерки

1. **Никога цял файл** — нито от Fable, нито като артефакт. Ползвай
   съществуващия модел „файлове >25 KB се пачват през Python скрипт в
   GitHub Actions" или директен GH патч. И двете спестяват ~10x токени.
2. **Разбий монолита.** Модули + билд стъпка, която ги слепва в single-file.
   Offline-first изходът се запазва, редакцията пипа 3k вместо 45k токена.
3. **Нов чат за всяка задача.**
4. **Таван на разхода** в Settings → Usage → Adjust limit. Дръж го нисък.

## 7. Инструкция за Claude (за User Preferences / Project instructions)

> Преди да започнеш задача, кажи ми кой модел е правилният за нея:
> Haiku (чист превод, преформатиране на данни, regex с вече зададен
> шаблон — без логика на код), Sonnet (по подразбиране за рутинен код по
> съществуващи файлове, вкл. GitHub-first read/patch/upload: поправка на
> бъгове, скрейпъри, парсъри, селектори), Opus (дебъг с разсъждение върху
> няколко файла, рефактор, архитектурно ревю), Fable (само нова архитектура
> от нула). Предпочитай GitHub MCP четене/патч/качване пред артефакти, когато
> се пипа файл в репо — и без модел изобщо за чиста диагностика
> (curl/diff/build логове), преди да избереш модел. Ако съм във Fable за
> нещо, което Opus може — кажи ми да сменя, преди да пишеш код. Никога не
> връщай цял файл; давай само променената функция или патч. При счупен
> скрейп първо ме питай проверил ли съм източника ръчно.
